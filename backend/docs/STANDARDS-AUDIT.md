# Аудит: насколько это «java middle backend»

Честная оценка без комплиментов. Формат: утверждение → вердикт (✅ есть /
⚠️ спорно / ❌ нет) → что делать. В конце — приоритетный план.

Сразу главное: **это не учебный проект «на троечку», но и не эталон middle+**.
Основные слои, транзакции, безопасность и тесты сделаны по учебнику; не хватает
того, что отличает «работает» от «работает в команде годами»: версионирования
сущностей, наблюдаемости, CI, контрактных тестов и пары архитектурных решений,
которые в middle-команде попросят переделать.

---

## Сводная таблица

| Блок | Оценка | Коротко |
|---|---|---|
| ООП | ✅ | инкапсуляция, композиция, неизменяемые DTO; анемичные сущности — осознанно |
| SOLID | ⚠️ | S и D в порядке, LSP негде, ISP частично (толстые сервисы), OCP — слабое место |
| Spring (DI, стереотипы, конфиг) | ✅ | конструкторная инъекция, `@ConfigurationProperties`, профили |
| Spring Security | ✅ | stateless JWT, BCrypt, единый 401/403, IDOR закрыт |
| Spring Data JPA | ⚠️ | derived/JPQL/flush/N+1 — хорошо; нет `@Version`, проекций, спецификаций |
| Транзакции | ✅ | `@Transactional` в сервисах, `readOnly`, откат на unchecked |
| Многопоточность | ⚠️ | бины stateless, гонки закрыты constraint'ами; нет оптимистичных локов |
| Валидация | ✅ | Bean Validation на входе, CHECK/FK/UNIQUE в БД |
| Обработка ошибок | ⚠️ | единый формат, но `Map<String,Object>` вместо типа; 404-пути не настроены |
| Тесты | ⚠️ | 12 тестов, включая сквозной HTTP; нет Testcontainers и тестов на чужой доступ |
| Наблюдаемость | ❌ | нет actuator, метрик, структурных логов |
| API-дизайн | ⚠️ | REST-ish, но нет версии, пагинации у списков, идемпотентности |
| Эксплуатация | ❌ | нет Dockerfile/compose, CI, миграций на прод, конфигурации окружений |
| Читаемость | ✅ | имена, комментарии «почему», размер файлов в норме |

## 1. ООП

**Инкапсуляция** ✅. Поля `private`, доступ через методы; `final` у зависимостей
сервисов; `ApiException.status` — `private final` с геттером, а не публичное поле.

**Композиция вместо наследования** ✅. Наследование используется ровно там, где
это контракт фреймворка (`extends OncePerRequestFilter`, `extends RuntimeException`),
и нигде больше. Сервисы не наследуются друг от друга — вместо этого внедряются.

**Абстракция** ⚠️. Абстракции есть на уровне фреймворка (`JpaRepository`,
`PasswordEncoder`), но своих интерфейсов у сервисов нет:

```java
@Service
public class WeekService { ... }      // нет interface WeekService
```

В middle-команде это часто требуют («программируй к интерфейсу»), и вот честный
расклад:

- **За**: интерфейс даёт точку подмены (мок в тестах другого сервиса), позволяет
  JDK-прокси, документирует контракт.
- **Против**: у класса ровно одна реализация, подмены нет, моки делать умеет и
  Mockito по классу. Интерфейс «на всякий случай» — это дублирование 100 строк
  без пользы (YAGNI).

Правильный ответ для middle: **интерфейс нужен, когда есть/планируется вторая
реализация или когда сервис — точка расширения**. Здесь — нет. Если ревьюер
настаивает, добавление интерфейсов не сломает ничего, но это ритуал.

**Полиморфизм** ⚠️. Реального полиморфизма почти нет: `ApiException` с разными
фабриками — это один класс, а не иерархия. Вариант «по-книжному» — сделать
`NotFoundException extends ApiException`, `ConflictException extends ApiException`
и ловить базовым хендлером. Плюс: типобезопасность на catch. Минус: 5 классов
вместо одного. Сейчас выбран прагматичный вариант, и это нормально.

**Анемичная модель** ⚠️. Сущности — почти без поведения. В DDD это назвали бы
«антипаттерном», в CRUD-приложении — нормой. Альтернатива: `WorkoutEntry.addSet(...)`
с проверкой инвариантов внутри сущности. Плюс: инвариант нельзя нарушить даже
из нового сервиса. Минус: сущность начинает зависеть от бизнес-правил и её
сложнее маппить/тестировать. Для текущего размера — ок, но знать про это надо.

**Records** ✅. DTO — record'ы: неизменяемость, `equals/hashCode`, меньше кода.
Это современный Java-стиль (17+), на middle его ждут.

## 2. SOLID по буквам

### S — Single Responsibility ⚠️

Хорошо: `JwtService` только токены, `ExerciseService` только библиотека,
`GlobalExceptionHandler` только ошибки.

Плохо: **`SettingsService` знает про упражнения**.

```java
public class SettingsService {
    private final ExerciseRepository exerciseRepository;   // чужая ответственность

    private List<String> replaceGroups(...) {
        exerciseRepository.reassignMuscleGroup(userId, group, UNASSIGNED_GROUP);
```

Причина — требование «удалил группу → упражнения не осиротели», и делать это
надо в одной транзакции. Но класс теперь меняется по двум причинам: изменились
настройки **или** изменились правила библиотеки упражнений.

Как чинить, не теряя атомарности:
1. `ExerciseService.reassignGroup(userId, from, to)` с `@Transactional`, вызвать
   из `SettingsService` (транзакция REQUIRED — сольётся в одну);
2. или доменное событие `MuscleGroupRemoved` + `@TransactionalEventListener`
   (`BEFORE_COMMIT`), чтобы развязать слои совсем.

Второй вариант — «как в книжках», но он сложнее в отладке. Первый — то, что
обычно и делают в middle-командах.

### O — Open/Closed ⚠️

Слабое место. `SettingsService.toResponse` и `EntryResponse` собираются вручную;
добавление поля = правка 3-4 мест (DTO, сервис, тест). Это не нарушение само по
себе, но «расширение без изменения» не выполняется.

Где OCP соблюдён: `GlobalExceptionHandler` — новый тип ошибки = новый
`@ExceptionHandler`, существующие не трогаются. `JpaRepository` — новый запрос =
новый метод, генерация из имени.

Что можно улучшить: маппинг через MapStruct (новое поле = правка интерфейса +
аннотации, остальное генерируется).

### L — Liskov ⚠️ (нечего нарушать)

Наследования почти нет, LSP проверять не на чем. Единственный кандидат —
`ApiException` vs `RuntimeException`: контракт не ослаблен (не бросаем
checked, не сужаем), так что ✅ в рамках имеющегося.

### I — Interface Segregation ⚠️

Интерфейсы репозиториев — толстые (`JpaRepository` тянет 20 методов, из которых
используются 2-3). Это стандарт Spring Data, и «сегрегировать» его никто не
будет. Своих интерфейсов нет, поэтому нарушать нечего.

Если делать по-строгому: `interface ExerciseReader { List<Exercise> ... }` для
тех, кому нужно только чтение. В 95% проектов этого не делают.

### D — Dependency Inversion ✅

Сервисы зависят от интерфейсов репозиториев (`ExerciseRepository`), а не от
`EntityManager`. `PasswordEncoder` — интерфейс, `BCryptPasswordEncoder` —
реализация, внедряется бином. Контроллеры зависят от сервисов, не от JPA.

Чего нет: сервисы не зависят от абстракций **своего** уровня (см. S/абстракция),
и `SettingsService` тянет `ExerciseRepository` напрямую, минуя `ExerciseService` —
это как раз нарушение D «между модулями».

## 3. Spring

**DI через конструктор** ✅ — везде. Это правильный выбор: зависимости `final`,
объект нельзя создать в невалидном состоянии, нет рефлексии на полях, тест
пишется как `new WeekService(repo1, repo2, ...)`.

**Стереотипы** ✅: `@RestController`, `@Service`, `@Configuration`, `@Component`
(фильтр). `@Repository` не нужен — Spring Data сам помечает прокси.

**Конфигурация** ✅: `@ConfigurationProperties` + record + валидация в компактном
конструкторе. Это современнее, чем `@Value` на 10 полей.

**Профили** ✅: `application-dev.yml` + `@ActiveProfiles("dev")` в тестах.

**Транзакции** ✅: аннотация на сервисах, не на контроллерах и не на репозиториях;
`readOnly` там, где только чтение. Propagation по умолчанию (REQUIRED) —
`createDefaults` из `register` войдёт в ту же транзакцию, что и создание
пользователя: если упадёт создание настроек, откатится и пользователь.

**MVC** ✅: контроллеры тонкие, `@Valid` на теле, `@ResponseStatus` для кодов.

**Ошибки** ⚠️: формат единый, но реализация через `Map<String, Object>` — не
типобезопасно, нет автодополнения, легко опечататься в ключе. Правильнее:

```java
public record ApiError(OffsetDateTime timestamp, int status, String error,
                       String message, String details) { }
```

Исправить за 15 минут, польза — контракт ошибки виден в коде и в OpenAPI.

**Чего не хватает по Spring (важно для middle):**

| Чего нет | Зачем |
|---|---|
| `spring-boot-starter-actuator` | `/health`, `/metrics`, `/info` — без них деплой «вслепую» |
| OpenAPI (`springdoc-openapi`) | сваггер: фронт видит контракт, не читая код |
| `@ControllerAdvice` для 404 | запрос на несуществующий путь отдаёт дефолтный JSON Spring, не наш формат |
| Логирование запросов (MDC, traceId) | без него разбор инцидента — гадание |
| `spring.mvc.problemdetails.enabled` | RFC 7807 вместо самодельного формата |

## 4. Spring Data JPA

**Что сделано правильно:**

- ✅ derived queries для простых случаев, JPQL — где имя нечитаемо;
- ✅ `@Modifying` + `int` возврат для bulk update;
- ✅ `Pageable` вместо ручного `LIMIT`;
- ✅ `flush()` там, где порядок INSERT/DELETE критичен (это ловят на ревью чаще
  всего — и здесь это уже поймано тестом);
- ✅ N+1 решён явно: 3 запроса на список недель;
- ✅ `open-in-view: false` — сессия не живёт дольше транзакции;
- ✅ `ddl-auto: validate` + Liquibase: схема под контролем миграций;
- ✅ проверка владения в запросе (`findOwned`), а не после загрузки.

**Чего не хватает:**

| Проблема | Почему важно | Как исправить |
|---|---|---|
| ❌ нет `@Version` | два параллельных PUT настроек = «потерянное обновление» (last write wins) | добавить `version bigint` + `@Version` в `UserSettings`, `WorkoutEntry` |
| ⚠️ нет проекций | `findAll` тянет все колонки, даже если нужны 2 | interface-based projections для списков |
| ⚠️ нет `Specification`/Criteria | фильтры «по группе + по имени + по дате» начнут плодить методы | `JpaSpecificationExecutor` когда фильтров станет 3+ |
| ⚠️ нет batch-insert | 50 подходов = 50 INSERT'ов | `hibernate.jdbc.batch_size=50` + `rewriteBatchedStatements` |
| ⚠️ нет second-level cache | каждое чтение — в БД | нужно ли? для этого приложения — нет, но знать про `@Cacheable` надо |
| ⚠️ `EntityManager` после `@Modifying` | см. раздел про `clearAutomatically` | добавить флаг при первом же баге |

**Отдельно про отсутствие связей** (`@ManyToOne`). Это осознанный trade-off
(подробно — в `CODE-WALKTHROUGH.md`). На собеседовании это хороший ответ, если
умеешь объяснить: «нет N+1, нет прокси, предсказуемые запросы, ценой ручной
склейки». Плохой ответ — «я не умею связи». Разница между middle и junior
именно в этом.

## 5. Многопоточность

Это раздел, где junior обычно плывёт, поэтому подробно.

**Что объективно в порядке:**

1. **Бины — singleton и stateless.** `WeekService` не хранит состояние между
   вызовами: все данные — локальные переменные или параметры. Значит, один
   экземпляр безопасно обслуживает все потоки Tomcat.
2. **`SecurityContextHolder`** — ThreadLocal: контекст не «протекает» между
   запросами (при условии, что фильтр его очищает; Spring делает это сам в
   `SecurityContextPersistenceFilter`/`SecurityContextHolderFilter`).
3. **`JwtService`** — единственное место с криптографией: `Mac` создаётся
   локально на вызов, `SecretKeySpec` неизменяем, `JsonMapper` потокобезопасен.
4. **`EntityManager` не шарится** между потоками: Spring даёт каждому потоку свой
   через `TransactionSynchronizationManager` (ThreadLocal). Поэтому `@Transactional`
   и «один поток — одна транзакция» работают.
5. **HikariCP** — пул соединений: 10 соединений по умолчанию, остальные потоки
   ждут. Это не «многопоточный код», но именно здесь появляются узкие места.

**Гонки, которые есть в системе, и чем закрыты:**

| Сценарий | Что может пойти не так | Защита сейчас |
|---|---|---|
| Две регистрации с одним email | дубликат пользователя | `UNIQUE (email)` + 409 |
| Две заявки в друзья навстречу | две строки на одну пару | `UNIQUE (low, high)` + 409 |
| Создание одной недели двумя запросами | две недели на один `week_start` | `UNIQUE (user_id, week_start)` |
| Два PUT настроек одновременно | потерянное обновление (последний победил) | **нет защиты** ❌ |
| Два PUT одной записи | то же | **нет защиты** ❌ |

Для последних двух и нужен `@Version` (оптимистичная блокировка): Hibernate
добавит `where version = ?` и при конфликте бросит
`OptimisticLockingFailureException` → 409. Сейчас этого нет, и для приложения на
одного пользователя это терпимо, но в терминах «middle» — пробел.

**Чего нет и не должно быть:** `synchronized`, `volatile`, свои `Thread`,
`ExecutorService`. В веб-приложении на Spring ручная многопоточность — почти
всегда ошибка: масштабирование делается пулом Tomcat и пулом соединений, а не
потоками в коде. Если понадобится фоновая задача (пересчёт статистики) — тогда
`@Async` + `TaskExecutor` с ограниченным пулом, и это отдельное решение.

**Что стоит проверить при нагрузке:** размер Hikari-пула vs количество потоков
Tomcat. По умолчанию Tomcat 200 потоков, Hikari 10 соединений — при 50
одновременных запросах 40 потоков будут ждать соединение. Настраивается
`spring.datasource.hikari.maximum-pool-size`. Это классический вопрос на
собеседовании.

## 6. Безопасность

**✅ Сделано:**

- BCrypt с солью, пароль не хранится и не логируется;
- JWT подписан HMAC-SHA256, подпись сравнивается за постоянное время;
- `sub` = id пользователя, `exp` проверяется;
- нет user enumeration (одинаковый ответ на «нет email» и «неверный пароль»);
- IDOR закрыт: `findOwned`, `findByIdAndUserId` — чужой id даёт 404;
- 403/404 не дают перебором узнать существование объектов;
- DTO на входе → нельзя «mass assignment» (передать `id`/`role` и записать их);
- CORS ограничен списком origin;
- CSRF отключён осознанно (не cookie-аутентификация);
- наружу не уходят тексты исключений.

**❌ Чего нет (и это нормально для учебного, но не для прода):**

| Пробел | Риск |
|---|---|
| нет rate limiting на `/auth/login` | брутфорс пароля; BCrypt замедляет, но не спасает |
| нет отзыва токена | уволенный сотрудник/украденный токен живут 12 часов |
| нет refresh-токенов | плохой UX: логин каждые 12 часов |
| секрет в `application.yml` по умолчанию | забыли `JWT_SECRET` → все инстансы с известным ключом |
| нет HTTPS-требования | токен по HTTP = перехват |
| нет аудита действий | невозможно понять, кто удалил тренировку |
| нет проверки сложности пароля | только длина 8 |
| нет 2FA, нет OAuth | — |

Про `JWT_SECRET`: правильно — падать на старте, если переменная не задана, а не
подставлять dev-значение. Сейчас подставляется (удобно для тестов), в проде это
надо переключить профилем.

## 7. Тестирование

**✅ Что есть и почему это неплохо:**

- unit-тесты криптографии (быстрые, без Spring);
- тест календарной логики на границах;
- «контекст поднимается» — ловит рассинхрон миграций и маппинга;
- сквозной HTTP-тест через настоящий порт: security-фильтр, сериализация,
  статусы — то, что MockMvc не проверяет полностью;
- тесты проверяют **бизнес-правила**, а не геттеры: перенос группы в `Unassigned`,
  сохранение денормализованной группы в логе, удаление пустой недели.

**❌ Чего не хватает для middle:**

| Пробел | Как закрывать |
|---|---|
| нет теста «чужой entry → 404» | `ApiFlowTest`: второй пользователь, чужой id, ожидаем 404 |
| нет тестов друзей | accept/decline/remove, дубль заявки, заявка самому себе |
| нет теста `@Version`-конфликта | после добавления `@Version` |
| H2 вместо PostgreSQL | `Testcontainers` + `postgres:16` — тесты на реальной БД, а не на «похожей» |
| нет тестов на границы (`limit=0`, `limit=99999`) | параметризованные тесты |
| нет проверки JSON-схемы | JSON Schema / snapshot-тесты контракта |
| нет покрытия (JaCoCo) | метрика не самоцель, но 60-70% на сервисах — ориентир |

Важно: **H2 ≠ PostgreSQL**. `MODE=PostgreSQL` не эмулирует всё (типы, `ON
CONFLICT`, поведение `NULL` в индексах, блокировки). Поэтому «тесты зелёные» не
гарантируют, что на Postgres всё хорошо. Testcontainers решает это ценой
Docker в CI.

## 8. Наблюдаемость и эксплуатация

❌ Здесь самых больших пробелов.

- нет `actuator`: нечего дергать healthcheck'ом в k8s/докере;
- нет метрик (сколько запросов, сколько 5xx, время ответа);
- нет структурных логов (JSON) и `traceId` в MDC — по логам нельзя связать
  запрос и ошибку;
- нет Dockerfile / `docker-compose.yml` с Postgres;
- нет CI (GitHub Actions): тесты гоняются только локально, «зелёный main» не
  гарантирован;
- нет стратегии миграций на прод (Liquibase есть, а пайплайна нет);
- нет конфигурации для нескольких окружений (`application-prod.yml`).

Для учебного проекта это нормально. Для вакансии «middle» на вопрос «как
выкатываешь?» нужен ответ хотя бы уровня: «Dockerfile multi-stage, compose с
Postgres, GitHub Actions: build → test → образ, миграции при старте, healthcheck
по `/actuator/health`».

## 9. API-дизайн

**✅ Хорошо:** ресурсы во множественном числе, правильные методы и коды
(201/204/409/401), вложенность `/weeks/{date}/entries`, единый формат ошибок,
даты в ISO.

**⚠️ Спорно:**

- **`PUT /api/settings` — полная замена.** Логично для «формы настроек», но
  клиент обязан присылать все поля, иначе они сбросятся в дефолт. Для
  частичного обновления нужен `PATCH`. В текущем коде `null` в `unit` означает
  «не менять», а `muscleGroups = null` — «не трогать группы», то есть PUT уже
  наполовину PATCH. Это надо либо задокументировать, либо привести к одному
  стилю.
- **Нет версионирования** (`/api/v1/...`). Пока клиент один — не проблема; как
  только мобилка и веб начнут расходиться — понадобится.
- **Нет пагинации** у `/api/weeks` и `/api/exercises` (у весов есть `limit`).
  Сейчас ограничено 8 неделями по умолчанию — приемлемо, но неявно.
- **Нет `ETag`/`If-None-Match`**, нет кэш-заголовков.
- **Нет идемпотентности** для POST (заголовок `Idempotency-Key`): двойной клик
  «добавить тренировку» создаст две.
- **404 на неизвестный путь** отдаёт стандартный JSON Spring, а не наш формат.

## 10. Код-стайл и читаемость

**✅ Сильные стороны:**

- имена отражают смысл (`usualWeightLbs`, `reassignMuscleGroup`,
  `findOwned`), нет `data`, `info`, `tmp`;
- комментарии объясняют **почему**, а не «что» (`// Hibernate runs inserts before
  deletes in a single flush`);
- файлы небольшие: самый большой `WeekService` — 218 строк, и он разбит на
  приватные методы по смыслу;
- нет «магических» строк: `Friendship.STATUS_ACCEPTED`, `UNASSIGNED_GROUP`;
- единый стиль отступов, нет закомментированного кода;
- нет Lombok — спорно, но осознанно: явные геттеры/сеттеры читаются новичком
  без «магии» и не требуют процессора аннотаций. В команде Lombok почти всегда
  есть; аргумент против — скрытые `equals/hashCode`, проблемы с `@Data` на
  JPA-сущностях.

**⚠️ Что бы поправил:**

- `WeekService` — на грани. Три ответственности: нормализация дат, CRUD записей,
  сборка DTO. Можно вынести `WeekMapper`;
- `GlobalExceptionHandler` — 5 почти одинаковых методов `build(...)`, можно
  свернуть;
- `SettingsService.clean()` бросает исключение из метода, который называется
  «clean» — по имени не ожидаешь исключения. Назвать `validateAndClean`;
- в `FriendService.list()` три `if/else` про статусы — просится enum/метод
  `bucketOf(friendship, userId)`.

## 11. Что значит «middle» и где ты относительно него

Ориентир по блокам (не по годам опыта):

| Навык | Junior | Middle | Здесь |
|---|---|---|---|
| Слои и DI | путает | держит границы | ✅ |
| JPA | `findAll` и связи | понимает N+1, транзакции, flush | ✅ с оговорками |
| Транзакции | «аннотация магическая» | понимает прокси, откат, propagation | ✅ |
| Безопасность | «добавил JWT» | понимает IDOR, enumeration, stateless | ✅ |
| Ошибки | 500 на всё | коды, единый формат, логи vs ответ | ⚠️ формат не типизирован |
| Тесты | «работает же» | unit + интеграционные, понимает разницу | ⚠️ нет Testcontainers |
| Конкурентность | не думает | видит гонки, знает про локи | ⚠️ нет `@Version` |
| Эксплуатация | «локально работает» | Docker, CI, health, метрики | ❌ |
| API-дизайн | «лишь бы фронт доволен» | версии, пагинация, идемпотентность | ⚠️ |

Итог: **код тянет на middle в части «написать сервис»**, но не в части
«эксплуатировать сервис». Второе — ровно то, что спрашивают на собеседованиях
после того, как ты рассказал про контроллеры.

## 13. Как объяснять это на собеседовании

Три вопроса, которые почти наверняка зададут по этому коду, и хорошие ответы:

**«Почему у сущностей нет связей `@ManyToOne`?»**
> Потому что API читает агрегаты целиком, а не гуляет по графу. Со связями я бы
> получил N+1 на списке недель и `MultipleBagFetchException` при двух
> коллекциях. Я загружаю тремя запросами и склеиваю в DTO. Цена — ручная
> склейка; выигрыш — предсказуемые запросы и никаких `LazyInitializationException`.

**«Как защищён доступ к чужим данным?»**
> Владение проверяется в самом запросе: `findOwned(entryId, userId)` джойнит
> `workout_weeks` и фильтрует по `user_id`. Чужой id возвращает 404, а не 403 —
> чтобы нельзя было перебором узнать, существует ли запись.

**«Что будет при двух одновременных запросах?»**
> Там, где есть уникальный бизнес-ключ (email, неделя, пара друзей), стоит
> UNIQUE-индекс, и второй запрос получает 409 из обработчика
> `DataIntegrityViolationException`. Где такого ключа нет (настройки, запись),
> сейчас last-write-wins — это известный пробел, закрывается `@Version`.

Если можешь рассказать эти три вещи и показать, где в коде это лежит, — уровень
«middle» по этому проекту защищён.
